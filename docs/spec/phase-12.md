# Phase 12 — Parity pass and CI

Phases 2–11 each built a slice of the app against the discovery screens they covered. Nothing has
yet looked at **the whole app against the whole of discovery at once**, and nothing in CI runs on a
push to a branch that is not a pull request. This phase does both:

- **The parity pass.** Every discovery screen (#01–#107, 55 captures) gets a clone screenshot taken
  at the same state, by a Maestro flow tagged `parity`. An agent reads each pair side by side with
  the Read tool and writes one row per screen into **`docs/parity/REPORT.md`**. Every difference is
  graded `must`, `should` or `wont` (§4). A `must` is either fixed in this phase, with a flow that
  proves the fix, or deferred with a reason in `docs/plan/BLOCKERS.md`. The phase cannot exit with a
  `must` whose status is `open`.
- **CI.** `.github/workflows/ci.yml` already runs `check`, `test`, `build` and `deploy:check` on a
  pull request into `main`. It gains a `push` trigger on every branch. A new gate script pins the
  workflow's shape, so that a later edit cannot quietly drop the push trigger, float the Bun
  version, or add a macOS or Maestro job (§7).

**Maestro stays local** (decided 2026-09-25, phases.md). CI gets no macOS runner and no Maestro
job. The E2E check is the full local suite, run once at this phase's gate (§8, AC12).

**References and ids.** `#NN` is `~/personal/granola-clone-discovery/screens/NN-*/`. Its `shot.png` is
1284×2778 (3× of 428×926pt, iPhone 14 Plus). The clone runs on the iPhone 17 Pro simulator
(402×874pt, 1206×2622 at 3×). So a horizontal measurement is compared as an **inset from the
nearer edge**, not as an absolute x, and vertical positions are compared from the top safe area.
Tokens are the discovery README's, as implemented in `apps/native/src/design/tokens.ts`.

**Branding.** The report, the flows and every fix follow the phases.md rule: the app is "Notes". A
discovery string that names the product is compared against its **Notes** form, never against the
original (§5). The discovery screenshots stay outside the repo. The report names them by path and
never copies or embeds them.

## 2. The parity loop

```
bun run e2e:ios                                   (terminal 1: dev client + Metro on :8081)
bun run dev:api                                   (terminal 2: local API on :3001, harness on)
bun run parity                                    (terminal 3: = bash scripts/parity.sh)
   └ maestro --device <UDID> test --include-tags parity apps/native/.maestro
        └ each phase-12/parity-*.yaml ─ takeScreenshot parity-NN-<slug>
   └ moves every parity-*.png into artifacts/parity/<YYYY-MM-DD>/
agent: for each #NN
   Read ~/personal/granola-clone-discovery/screens/NN-*/shot.png
   Read artifacts/parity/<date>/parity-NN-<slug>.png
   → a row in docs/parity/REPORT.md (§4.5)
fix each `must` → a flow proves it → re-run its capture flow → mark the row `fixed`
```

### 2.1 `scripts/parity.sh`

It is a copy of `scripts/maestro.sh`'s preamble: the same UDID default
(`351547D8-BD3B-4418-AB30-8568D8FFB8F3`), the same Metro probe, and the same `E2E_SECRET` read from
`apps/api/.dev.vars`. It then does this:

1. It runs `maestro --device "$UDID" test --include-tags parity -e … apps/native/.maestro` from
   inside a fresh `artifacts/parity/<YYYY-MM-DD>/` directory. Maestro resolves a relative
   `takeScreenshot` path against its working directory, so the shots land there. If the installed
   Maestro resolves it elsewhere, the script passes `--test-output-dir` to the same directory
   instead. The builder checks which case applies once and leaves a comment saying so.
2. It exits non-zero if any flow failed, **and** if the directory holds fewer PNGs than the number
   of `takeScreenshot: parity-` lines under `phase-12/`. A flow that passes without reaching its
   screenshot has proven nothing about parity.
3. It never names a physical device. The physical iPhone (`00008110-000C6D612251401E`) is off
   limits.

`package.json` gains `"parity": "bash scripts/parity.sh"`. `.gitignore` gains `artifacts/`.

### 2.2 Screenshots in ordinary runs

The parity flows are also in the full suite (config.yaml lists `phase-12/*`), because every one
asserts the testIDs of the state it reaches, and that is a real regression check. Run that way,
their `takeScreenshot` files land wherever the suite's Maestro was started, as every earlier
phase's screenshots already do. `artifacts/` is the only place the report reads from.

## 4. How a pair is graded

### 4.1 What is compared, in order

1. **Structure.** The same controls, in the same order and grouping, on the same kind of surface
   (pushed page, full sheet, half sheet, card sheet, drawer, menu).
2. **Copy.** Every visible string and a11y label from COPY.md, with the product name as Notes (§5).
3. **Colour.** Each fill, border and text colour maps to the same token (the README's table). A
   sampled hex within ±6 per channel of the token counts as the same colour: the discovery hexes
   are themselves samples.
4. **Type.** Serif display where discovery uses serif (page titles, empty-state headlines, note
   titles, sheet titles). SF Pro everywhere else, with the size and weight of the README's scale:
   row titles 17 semibold, body 17, section headers 15–17 grey, nav titles 20 semibold.
5. **Geometry.** Radii (pills fully round, cards 24–28, sheet tops ~40, list tiles ~10), 44pt
   circular icon buttons, gutters (inset from the nearer edge), row heights and vertical rhythm.
   A difference of 4pt or less is not a gap.
6. **Behaviour visible in the shot.** Pinned vs scrolling chrome, a scrim and its dim, a disabled
   state that looks disabled, and a keyboard that does not cover the control the screen is about.

### 4.2 Severity

| Grade | Means | Examples |
| --- | --- | --- |
| **must** | A user would notice it in a core journey, or it breaks a rule: a control that is missing, dead, unreachable or on the wrong surface; wrong copy; a Granola string; a colour on the wrong token; text clipped or overlapping; a serif/sans swap on a title; a layout off by more than 12pt; a keyboard covering the screen's own control | #90's Diagnostics row under the keyboard (§6.2) |
| **should** | Visible side by side but not in use: a 5–12pt spacing drift, a glyph that differs in weight or shape, a shadow or blur material that differs, a divider inset | lucide vs SF Symbols glyph shapes |
| **wont** | Deliberate, and recorded with its reason: branding, out-of-scope features, seed content, platform-owned chrome, or a decision an earlier phase spec records | the serif substitute; neutral model names |

Anything the grader is unsure of is a `should`, never silently dropped.

### 4.3 States discovery never saw

The clone has states discovery never captured, designed in their phase specs (loading, error, the
populated events card, folder lists, onboarding, welcome). They have no row, because the report is
indexed by discovery screen. The one check the pass makes on them is a **visual-language
sweep**. The grader opens the screenshots earlier phases' flows already take (for example
`phase-11-events-card`, `phase-9-folder-list`) and grades any off-token colour or off-scale type as
a `should`, listed in the report's last section, "Designed states".

### 7.1 `.github/workflows/ci.yml`

```yaml

    branches: ["**"]
```

  cancels the older run.

  `bun-version`;
- no job in either file has a `runs-on` containing `macos`, and no step's `run` or `uses` mentions
  `maestro`;
- `ci.yml`'s verify job runs `bun run check` and `bun run test`, in that order;
- the root `package.json` `packageManager` matches `^bun@\d+\.\d+\.\d+$` (exact, no range).

Each rule is a pure function `(workflows, pkg) → string[]` in `scripts/lib/ci-rules.mjs`, so the
tests (§9.2) run it on inline fixtures.
